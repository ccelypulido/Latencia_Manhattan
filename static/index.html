Sustento Técnico y Guía de Diagnóstico de Red

Fundamentos teóricos, metodología por capas TCP/IP y resolución de cuellos de botella

Arquitectura de Conexión Secuencial: Las peticiones HTTPS no son atómicas; se dividen en 5 etapas rigurosamente secuenciales a través de las capas OSI y TCP/IP.
1
Fase 1: Resolución DNS (dns_ms) Capa de Aplicación (UDP/53)

El cliente consulta a los servidores DNS configurados en el sistema operativo para traducir el nombre de dominio (ej. alkop.sce.manh.com) en una dirección IP destino (136.68.87.180).

socket.gethostbyname(hostname)
2
Fase 2: Handshake TCP (tcp_ms) Capa de Transporte (TCP)

Se establece el socket confiable mediante el 3-Way Handshake (SYN → SYN-ACK → ACK). Mide el tiempo puro de ida y vuelta de red (1 RTT) hacia el servidor o balanceador de Manhattan.

sock.connect((ip, port))
3
Fase 3: Negociación Criptográfica TLS / SSL (tls_ms) Capa de Seguridad / Presentación

Sobre el socket TCP ya abierto, se negocia el canal cifrado: intercambio de llaves Diffie-Hellman/ECDHE, validación de la cadena de certificados x509 del servidor y establecimiento del cifrado simétrico (1 a 2 RTTs + cálculo criptográfico de CPU).

ssl_context.wrap_socket(sock, hostname)
4
Fase 4: Espera del Servidor (TTFB - Time To First Byte) Capa de Aplicación (HTTP/1.1)

Tiempo que transcurre desde que se envía la solicitud HTTP (con sus cabeceras, cookies o autenticación) hasta recibir el primer byte de respuesta del servidor Manhattan. Evalúa el procesamiento en backend.

sock.sendall() → sock.recv(1)
5
Fase 5: Transferencia de Datos (transfer_ms) Capa de Transporte / Datos

Descarga completa del cuerpo de la respuesta HTTP a través de chunks en el socket hasta el cierre de la conexión o fin del Content-Length.

while sock.recv(8192)
Ecuaciones de Medición y Metodología de Navegador

Cada medición en este analizador se calcula mediante temporizadores monótonos de altísima resolución (time.perf_counter()). Para replicar con exactitud el comportamiento de las terminales PDA y navegadores web con conexiones persistentes (HTTP Keep-Alive), la aplicación distingue dos ecuaciones:

1. Latencia Operativa Navegador / PDA (Métrica Principal):
T_Total = T_TTFB + T_Transfer
Tiempo de respuesta efectivo de la petición HTTP en la terminal RF / Chrome.
2. Conexión en Frío Acumulada (Cold Start):
T_Cold = T_DNS + T_TCP + T_TLS + T_TTFB + T_Transfer
Tiempo total requerido si se abre un socket nuevo desde cero (incluyendo DNS y handshakes).

A diferencia de librerías de alto nivel que mezclan tiempos, el motor probe.py cronometra cada llamada al socket de forma aislada para garantizar que no exista duplicidad ni superposición en los milisegundos reportados.

Cero Dependencias Externas

El analizador está construido exclusivamente sobre la librería estándar de Python (socket, ssl, sqlite3, http.server). Esto garantiza que pueda desplegarse inmediatamente en cualquier terminal Windows, Linux o máquina corporativa restringida sin requerir pip install ni privilegios de administrador.

📱 ¿Por qué en la PDA y en Chrome la prueba da ~187 ms y antes sumaba ~386 ms?
En terminales PDA y navegadores como Google Chrome, las peticiones HTTP reutilizan conexiones persistentes (HTTP Keep-Alive). Cuando la PDA realiza la prueba a /ping, la conexión TCP y TLS ya está negociada, por lo que la latencia operativa percibida es puramente el tiempo de respuesta HTTP (TTFB + Transferencia = ~187 ms).

Si se sumariza la conexión en frío desde cero (apertura de socket TCP + TLS + HTTP), el tiempo total acumulado asciende a ~386 ms. El Manhattan Latency Analyzer adopta la metodología del navegador para la métrica principal, preservando al mismo tiempo el diagnóstico granular de Conexión Inicial (TCP + TLS) para aislar problemas de red.

Diagnóstico Integral y Preciso

Al alinear la latencia total con la metodología de navegador de la PDA, las métricas del sistema coinciden 1:1 con lo que experimenta el operario de bodega en sus pistolas de radiofrecuencia, permitiendo al mismo tiempo aislar caídas de red física gracias a las fases desacopladas de TCP y TLS.

Utiliza esta matriz de diagnóstico rápido para correlacionar picos en las métricas con su causa raíz más probable en la infraestructura:

Síntoma Métrica Elevada Causa Raíz Probable Acción Recomendada
DNS Lento dns_ms > 50 ms Servidor DNS local o corporativo sobrecargado, pérdida de caché o resolver recursivo distante. Verificar servidores DNS primario/secundario en la sede; evaluar servidores DNS locales más rápidos.
Red / ISP Lento tcp_ms > 100 ms Problema físico de canal, latencia RTT geográfica, congestión en el proveedor de internet o enlace WAN saturado. Ejecutar traceroute / MTR hacia 136.68.87.180; revisar canal SD-WAN y consumo de ancho de banda.
SSL Sobrecargado tls_ms > 150 ms Sobrecarga de CPU en el balanceador o terminador SSL de Manhattan; validación CRL/OCSP lenta. Verificar si el endpoint soporta TLS 1.3 (1-RTT); auditar la carga en el reverse proxy de Manhattan.
Backend Lento ttfb_ms > 400 ms Cola de peticiones en el servidor de Manhattan, base de datos ocupada o demora en el middleware de autenticación SSO. Revisar métricas internas de la aplicación Manhattan; verificar salud del servicio de ping.
Descarga Lenta transfer_ms > 20 ms Pérdida de paquetes, ventana TCP pequeña o saturación del ancho de banda local. Verificar calidad del enlace Wi-Fi/cableado y pérdida de paquetes en la red local.

Cuando se realizan pruebas en diferentes días o desde diferentes sucursales (ej. Sede Bogotá, Sede Medellín, Home Office), el sistema etiqueta cada muestra de latencia en la base de datos SQLite:

  • Etiqueta de Sede: Configurable desde el menú ⚙️ Configuración. Todas las pruebas realizadas desde ese equipo quedarán marcadas con esa sede.
  • Filtro Global: El selector de la barra superior actualiza de forma reactiva todas las tarjetas, gráficos y promedios para la sede elegida (o "Todas las Sedes").
  • Panel Comparativo entre Sedes: Contrasta en tiempo real el rendimiento relativo de cada oficina (Muestras, DNS, TCP, TLS, TTFB y Latencia Total).
  • Limpieza Contextual: Al pulsar Limpiar Histórico, el sistema detecta si estás filtrando una sede específica para borrar únicamente los registros de dicha sede sin tocar las demás.
  • Exportación a CSV / ZIP: El botón Exportar descarga únicamente los datos filtrados para generar informes independientes con su columna de zona.

Impacto de la Autenticación en la Medición de Latencia

El endpoint de ping de Manhattan puede requerir autenticación para responder con HTTP 200 OK. Este analizador soporta 3 modalidades:

1. Petición Anónima (Sin Autenticación):

Devuelve HTTP 401 o 403 Forbidden. El servidor rechaza la petición rápidamente, por lo que el TTFB puede verse artificialmente menor ya que no ejecuta la lógica de negocio.

2. Autenticación NTLM v2 (Dominio Active Directory):

Ejecuta el protocolo de desafío/respuesta de 3 vías (Type 1 Negotiate → Type 2 Challenge → Type 3 Authenticate) en Python puro sin dependencias externas sobre el mismo socket seguro.

3. Cookie de Sesión / Bearer (MFA Microsoft / Azure AD SSO):

Permite simular exactamente a un usuario logueado tras validar el doble factor (MFA). Al extraer la cookie desde el navegador (F12 → Red → Cookie: FedAuth=...; JSESSIONID=...), el analizador la inyecta entregando HTTP 200 OK y midiendo la latencia operativa real.

¿Por qué los Promedios no son Suficientes?

En operaciones logísticas y sistemas WMS de misión crítica, un promedio puede dar una falsa sensación de normalidad. Si 99 peticiones tardan 200 ms y 1 petición tarda 5000 ms (un congelamiento en la terminal de radiofrecuencia), el promedio dirá "248 ms (aparentemente bien)", pero el operador sufrió una detención crítica.

Percentil P95 El 95% de las peticiones fueron más rápidas que este valor. Estándar de SLA en Manhattan SCE.
Percentil P99 Refleja el peor 1% de las transacciones (los peores micro-picos o retrasos que perciben los usuarios).
Jitter (StdDev) Desviación estándar de latencia. Evalúa la estabilidad del canal. Un Jitter < 15 ms indica una red sumamente estable.
Aislamiento de Causa Raíz de Infraestructura: Para determinar si una degradación de latencia ocurre dentro de la LAN de la sede o en el proveedor de internet (ISP), el sistema realiza diagnósticos ICMP hacia 3 destinos clave.
1. Puerta de Enlace Predeterminada (Default Gateway)

Auto-detecta la IP del switch/router de borde local. Mide la latencia pura física de la sede (cableado, switches y cobertura Wi-Fi). Un tiempo < 3 ms y 0% pérdida garantiza que la red interna está en óptimas condiciones. Si supera los 10 ms o presenta pérdida de paquetes, el problema reside 100% en la sede local.

2. Servidores DNS Activos

Evalúa los resolutores configurados en la interfaz de red para comprobar si la Fase 1 (Resolución DNS) sufre retrasos por servidores DNS saturados o fallas en el Active Directory corporativo.

3. IPs Auxiliares y Traceroute Salto a Salto

Permite auditar nodos Core o WAN adicionales y despliega la ruta multi-salto (Hop-by-Hop) identificando con exactitud en qué router o salto del ISP se introduce latencia o pérdida de paquetes.
